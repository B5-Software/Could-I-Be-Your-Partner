# CIBYP native wallet signer

Development implementation; the complete multi-chain wallet plan is still open.

This Rust process has no RPC client, network listener or Agent tools. It receives bounded JSON requests through the parent's private stdin pipe and writes replies through stdout. Keys are generated with the operating system RNG, held in zeroizing buffers, and removed on lock, expiry, replacement or process exit. Unlock expiry uses a monotonic clock. Its persistent store contains signing receipts, not private keys or passwords. This is not OS isolation from arbitrary code running as the same user; locked pages, crash-dump suppression and hardware signing remain unfinished.

New wallets use a 256-bit, 24-word English BIP-39 phrase and `m/44'/60'/0'/0/0`. Supported signing remains EIP-1559 on Base and Base Sepolia. Derivation, secp256k1 signatures, Argon2id and AEAD use pinned libraries, not custom cryptographic primitives. Ethereum serialization is checked against ethers in process-level tests. Amounts use integer parsing; unsupported types, chains, access-list fields and invalid fee relationships are rejected.

## Encrypted backup format

`CIBYP-WALLET/1` is a JSON object containing `header` and hex `ciphertext`. The typed header is serialized in declaration order as AEAD associated data. It binds the format, version, random vault ID, account address, curve, KDF parameters/salt, cipher and nonce. Unknown fields are rejected. The decrypted payload contains the private key and, when available, the mnemonic and derivation path. Plaintext key material is not returned by unlock or signing.

New encryption uses Argon2id v19 (64 MiB, three iterations, one lane, 32-byte output), a fresh 32-byte salt and XChaCha20-Poly1305 with a fresh 24-byte nonce. Parameters and file sizes are bounded before expensive work. Device-dependent KDF calibration is not implemented. See [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html) and [libsodium's XChaCha20-Poly1305 documentation](https://doc.libsodium.org/secret-key_cryptography/aead/chacha20-poly1305/xchacha20-poly1305_construction).

Legacy Ethereum V3 import supports bounded scrypt and PBKDF2-HMAC-SHA256/SHA512, AES-128-CTR and a verified Keccak MAC. It supports existing ethers NFKC password normalization as a fallback to exact UTF-8 input. Ethers 0.1 encrypted English mnemonic metadata is decrypted, its derivation path preserved and its derived private key checked before recovery; unsupported extensions fail explicitly. Legacy cipher output is never used for new backups. Existing files change only after a user requests password rotation or imports a backup. Rotation locks the wallet and revokes local autonomous authority, without revoking on-chain approvals. Export a fresh backup after rotation.

256-bit authenticated encryption does **not** make an EVM wallet post-quantum: Base transaction signatures still use secp256k1. PQC wrapping, authenticated hardware-entropy pairing and external signing devices remain unimplemented. Current native authorization and budget controls are described below; this is not the complete cross-asset policy plan.

## Durable signing receipts

Internal pipe protocol 7 requires a store identity, stable operation ID and valid authority for signing. The handshake requires portfolio, Agent-scope and periodic-budget support. Wallet authority uses version 2. Before returning a usable signature, the signer commits a receipt to its bundled SQLite database using DELETE journaling, `synchronous=EXTRA` and `fullfsync=ON`. See [SQLite durability settings](https://www.sqlite.org/pragma.html#pragma_synchronous). These settings still depend on truthful filesystem and storage-device synchronization.

Receipts bind wallet ID, address, chain, nonce, canonical unsigned transaction hash and signed hash. The signed bytes are encrypted at rest with XChaCha20-Poly1305; HKDF-SHA256 derives a separate key from the unlocked wallet key, store identity and a fixed receipt domain. Receipt metadata is authenticated as associated data. Password changes preserve the wallet key, so existing receipts remain recoverable. Locked `receipt.get` returns only metadata and hashes, never signed bytes. Repeating the exact operation while unlocked and still authorized returns its original signature; reusing the ID with a different wallet, key or transaction fails.

A held file lock prevents parallel writers. Unix directories/files require private permissions; Windows inherits the profile directory ACL. Startup checks SQLite integrity, the committed count and every receipt checksum. A failed write poisons the connection until restart. A not-found recovery checks the complete ledger before it can release an unsigned reservation. The store is bounded to 200,000 receipts and 512 MiB; automatic archival is not implemented. An existing corrupt store is never silently recreated. Replacing or losing the store changes its identity and cannot prove an old operation was never signed. Checksums detect corruption; they do not prevent a privileged attacker from restoring an internally consistent old backup.

The backend persists its receipt binding before signing. Interrupted signing remains `signing-unknown`; nonce and budget reservations remain held. Recovery works while locked and only queries the native receipt and chain. It never signs or rebroadcasts automatically. Legacy interrupted operations without a receipt binding remain unresolved. Raw signatures and internal bindings are excluded from public intent responses.

## Native authority, nonce and fee ledger

Manual confirmations bind the canonical unsigned EIP-1559 hash, exact fee reservation, operation, derived signer address, deadline and current native unlock session. Lock/unlock or process restart changes the session; the old confirmation cannot sign or retrieve cached signed bytes. A denial persists an operation tombstone. The frontend digest separately binds the full prepared transaction, fee reservation, expiry and replacement reference, rather than only its original logical request.

Autonomous grants are persisted by the trusted private control plane and checked inside Rust against the wallet, derived address, chain, deadline and per-signature fee ceiling. Durable per-wallet generations prevent a late grant from overwriting a newer revocation. Grant, revoke, approve and sign are not public wallet actions or Agent tools. Old host-only grants need human renewal. This does not cryptographically attest a human click or isolate a compromised backend/OS account: the existing trusted UI and gateway remain part of the control-plane boundary.

Receipt insertion, nonce ownership, approval use, authorization usage and cumulative plan fee reservation commit in the same SQLite transaction. Plan wallet/address/chain/scope/budget cannot change under an existing plan ID. The fee reserve must cover `gasLimit * maxFeePerGas`; Base L1 costs still include a host-derived estimate, not a chain-enforced maximum. Fees of signed operations remain conservatively charged after a stop or lost reply; changing the grant or restarting does not reset a plan budget.

Native authority version 2 adds configurable per-signature ETH value, cumulative ETH value, cumulative fee reserve, signature count, outer destination and outer method-selector limits, plus a call-data switch. Grant usage commits atomically with the receipt and survives restart. A signature replay does not consume it again; a replacement does. Limits apply over the current grant, across its selected chains and plans. Zero amounts/counts and empty lists mean unlimited. A new explicitly confirmed human grant starts a new grant budget, while an existing plan's separate budget remains unchanged. Old grants without trustworthy aggregate counters are revoked during migration and need human renewal.

ETH value limits constrain only the outer transaction value. Optional token rules now add exact per-asset declared-effect budgets. Portfolio exposure, arbitrary internal contract effects, current onchain allowance monitoring and hierarchical child-agent scopes remain unfinished. GUI/WebUI and TUI share field catalogs and backend normalization; the review snapshot, including token rows, is frozen before the exact second confirmation.

## Declared token effects

The signer uses pinned Alloy Solidity ABI types, strict validation and exact re-encoding rather than an Agent-supplied transaction description. Rules identify up to 16 assets by chain and contract. Each may limit the total amount in one signature, the cumulative signed amount and an individual approval, disallow allowance increases, and restrict recipients/spenders. Human decimal amounts convert to exact uint256 atomic units, including uint8 token precision; symbols and decimals are display metadata, not evidence of contract identity.

Supported calls are canonical ERC-20 `transfer`, `approve`, and `transferFrom` from the signing account; official Base/Base Sepolia Uniswap V3 Router02 `exactInputSingle` and flat deadline `multicall` batches are also decoded. A batch has at most 16 calls and is bounded before ABI allocation. Every input and output token must be configured, swaps must return to the signer, input/minimum output must be positive, and router balance/recipient sentinels, nested batches, unknown methods and noncanonical/trailing data are rejected. Native-value wrapping/unwrapping and empty-calldata calls are not accepted under token rules: even empty calldata can invoke a contract fallback. Without token rules, existing ETH/outer-call policy behavior is unchanged; explicit manual signing remains separate from autonomous grant checks.

Approval and transfer/swap-input amounts count separately and together toward the cumulative token budget. This deliberately charges an approve-then-swap twice; it is a signature budget, not net loss or current allowance. Counters commit with the receipt in the same SQLite transaction, survive restart, and are not refunded on cancellation, no broadcast or a revert. A receipt replay is not charged twice. An allowance-reducing `approve(0)` remains possible when allowance increases are disabled. Trusted `authority.inspect` is read-only and usable while locked; GUI/WebUI/TUI and the Agent's public wallet reader show the same persisted counters.

Contracts remain trusted dependencies. ABI decoding cannot prove their execution behavior, stop reentrancy, revoke pre-existing onchain allowances, or prevent an external spender from using an existing allowance. No simulation/proof or general internal-call security claim is made. Source references: [ERC-20](https://eips.ethereum.org/EIPS/eip-20), [Uniswap Router02 interface](https://github.com/Uniswap/swap-router-contracts/blob/main/contracts/interfaces/IV3SwapRouter.sol), [router implementation](https://github.com/Uniswap/swap-router-contracts/blob/main/contracts/V3SwapRouter.sol), [deadline multicall](https://github.com/Uniswap/swap-router-contracts/blob/main/contracts/base/MulticallExtended.sol), [official Base deployments](https://developers.uniswap.org/docs/protocols/v3/deployments/v3-base-deployments).

The ledger retains signed nonces across cancellations, finality and restart. Reusing one requires a manual confirmation bound to its previous signed hash, or a human grant that explicitly enabled automatic replacement. Even that grant must pass the latest signed hash, remain authorized and obey its budgets; changing the operation ID alone is insufficient. GUI/WebUI and TUI show the default manual warning and expose the separate automatic switch, off by default. This currently handles reusing a known-unsent signed nonce, not a complete pending-transaction acceleration/replacement API; chain fee-bump rules remain pending. Schema migration reconstructs nonce ownership from existing receipts without touching key material.

## Cross-wallet portfolio signing budgets

A human may bind 1–16 named wallets to one portfolio on one Base network. Membership binds both wallet ID and actual signer address: omitting a portfolio ID or importing the same key under an alias cannot escape it. A wallet/address belongs to at most one unreleased portfolio per network. A portfolio constrains every new member signature, including explicit manual approvals, with the same native ETH, fee, count, target/method and optional declared-token rules. A wallet grant remains independently required for autonomous execution; creating/resuming a portfolio grants no wallet authority and starts no plan.

Portfolio usage, its signature links and the wallet/plan/nonce/receipt updates share one SQLite transaction. Wallet reauthorization, a different plan, restart and receipt replay do not reset or duplicate counters. Signature retrieval requires the same current portfolio link; a cached signature predating a new group cannot bypass its budget. Existing raw signatures already held elsewhere and pre-existing onchain allowances cannot be revoked by this mechanism. These are cumulative signed-amount limits, not portfolio valuations, current allowances, net exposures or loss guarantees.

Schema 5 retains membership counts and validates all portfolio bodies, membership bindings and usage counts on startup. Missing rows fail closed instead of silently making a member unrestricted. A verified schema-4 upgrade preserves the bindings and counters; damaged bindings fail migration. Earlier receipt/wallet formats remain intact. Portfolios are immutable budget epochs: pause/resume preserve usage, while release detaches members and retains history. Changing membership/limits currently requires an explicit human release and creation of a new budget; period rollover and edits preserving all counters remain future work.

The backend writes a separate durable local fence before a portfolio mutation and immediately aborts member operations. Epoch checks also cover manual broadcasts and prevent a late signature from being sent after a change. A failed/unconfirmed mutation keeps members fenced across restart. Human fence recovery verifies the native service and clears only the local fence; native pauses, expiry, membership and limits still apply. Creating, resuming, releasing and recovering require a separate frozen challenge and exact `ALLOW PORTFOLIO` confirmation. Global emergency stop invalidates outstanding portfolio challenges. The Agent tool can only page/read portfolios and request a scoped pause; it cannot grant, resume, release or clear a fence.

An explicitly rejected invalid creation removes only its own temporary local fence, so selecting an already-bound member does not permanently disable the wallet. An earlier unknown mutation's fence is preserved. Stale pause/resume/release requests still require reconciliation rather than silently clearing a stop.

As with wallet authority, these controls trust the UI/backend and OS account. A local fence write that fails is not claimed durable; the error is reported and the current process remains blocked. Counters and checksums do not resist an administrator restoring an internally consistent full snapshot. The tests verify defined boundaries, not universal wallet security.

## Inherited Agent signing scopes

Schema 6 adds immutable, per-chain Agent identities and a bounded parent graph. New autonomous wallet grants require trusted Agent identity/scope bindings. The backend supplies these from the quant session or persisted native subagent policy, never model arguments. Native `runSubAgent` uses the existing SDK continuation and isolated history. Quant children default to research tools; financial tools must be explicitly delegated and remain within the parent's whitelist. Other native child profiles do not acquire wallet authority.

Each child may narrow wallets, chains, expiry, transaction/ETH/fee caps, target/method restrictions and declared-token rules. Every scope in its ancestry is checked by the native signer. All ancestor charges, wallet/portfolio/plan counters, nonce ownership and the receipt commit atomically. Replaying an exact authorized signature does not charge twice; changing its leaf identity, reparenting or replacing a persisted scope is rejected. An Agent subject is unique on its chain. Continuation, new messages, backend restart and wallet reauthorization do not reset scope usage. A scope without extra caps still requires the independently human-approved wallet authority and portfolio budgets; it creates no signing permission.

Native scheduled plans persist their immutable Agent-scope ID/subject, so later dispatch and restart reconciliation retain the same ancestry. Legacy unscoped plans belong to the project root. Node guards fence late signatures before broadcast when an ancestor changes; an unconfirmed mutation preserves a separate local fence across restart. Agents may inspect ancestors/their subtree and pause themselves or descendants. Resume and local-fence recovery require a frozen human challenge and exact `ALLOW AGENT SCOPE`; recovery never clears native expiry, pauses or limits, and neither action unlocks a wallet or starts a plan. Existing externally held raw signatures cannot be revoked.

Startup validates the graph, metadata, usage counts and signature-to-ancestor links. Missing/modified records fail closed. Schema-5 migration adds empty scope tables without inventing authority or changing existing receipts. Scopes are immutable cumulative budgets, not periodic quotas, current allowance accounting or net exposure. Period rollover, in-place limit edits, hardware/PQC integration and the broader wallet plan remain incomplete. A trusted UI/backend and OS account are still required.

## Build and verification

`npm run prepare:wallet-signer` builds the locked Rust 1.99.1 target, signs macOS binaries before compression, and stages an architecture-checked, double-SHA-256-verified resource. The six target hosts follow the existing native runtime matrix. Installed applications refuse to borrow a developer binary if their resource is missing or corrupt.

`npm run test:wallet-signer` runs the locked Rust tests and exercises the actual process against ethers, including V3/HD recovery, metadata tampering, KDF limits, locking, exact signatures and encrypted creation. It also tests broken replies, backend crashes, locked recovery, operation conflicts, replaced stores, manual session binding, revocation generations, nonce confirmation, token/fee budgets across restart, ABI tampering, batch aggregation, shared cross-wallet counters and scope denial. `node tests/integration/wallet-native-signer.cjs --managed` additionally uses the staged resource/cache. Rust tests cover receipt/membership integrity and migration plus an independently generated legacy backup. Local-chain tests cover two real fixture wallets sharing a portfolio across manual ETH and scheduled token signatures, exact approval/swap counters and explicit nonce recovery. Synthetic fixture contracts are not a real Uniswap deployment. `npm run test:wallet-ui` uses the actual shared components with public fixture data for theme/layout, frozen token/portfolio review, named wallet selection, budget rendering, pause/resume review and replacement-reference forwarding.

Windows x64 is verified locally. Other target hosts still require native CI acceptance. These tests do not prove absolute security or resistance to every local attacker.
